# Тестирование

## Unit-тесты

`npm test` запускает `src/**/*.spec.ts` через Vitest. Зависимости сервисов
подменяются моками; PostgreSQL для этих тестов не требуется.

Дополнительные проверки: `npm run typecheck`, `npm run lint`, `npm run test:cov`
и `npm run build`.

## HTTP E2E-тесты

```bash
npm run test:e2e
```

Конфигурация `vitest.e2e.config.mts` запускает только `test/**/*.e2e-spec.ts`.
Тест создаёт настоящее Nest-приложение с `AppModule` и общей функцией
`configureApp`, отправляет HTTP-запрос через Supertest, проверяет ответ и
сохранённые данные в PostgreSQL. JWT, bcrypt и Prisma работают без моков.
Приложение слушает случайный свободный порт на `127.0.0.1` и закрывается после
каждого теста.

### Подготовка базы

Используется отдельная база `fakegram_e2e` на том же сервере PostgreSQL,
что и база разработки. Её нужно создать и применить к ней все существующие
миграции из `prisma/migrations` перед первым запуском тестов.

Команды ниже запускаются из корня репозитория после установки зависимостей.
Они используют локальные значения из `.env.example`: пользователь и пароль
`postgres`, порт `5432`. Если ты менял их, замени пользователя в командах и
данные подключения в URL. Имя тестовой базы должно оставаться `fakegram_e2e`.

1. Подними PostgreSQL из `docker-compose.yml` и проверь готовность:

   ```bash
   docker compose up -d db
   docker compose exec -T db pg_isready -U postgres -d postgres
   ```

   Дождись ответа `accepting connections`. Если сервер ещё запускается,
   повтори `pg_isready`.

2. Создай тестовую базу на этом сервере (один раз):

   ```bash
   docker compose exec -T db createdb -U postgres fakegram_e2e
   ```

   Если база уже существует, пропусти создание и примени миграции следующим
   шагом. Удалять существующую базу или данные разработки не требуется.

3. Создай локальный файл `.env.test.local` с подключением для E2E:

   ```dotenv
   E2E_DATABASE_URL=postgresql://postgres:postgres@localhost:5432/fakegram_e2e
   ```

   Файл уже добавлен в `.gitignore`. Если он существует, добавь или обнови
   в нём только `E2E_DATABASE_URL`. Используй тот же URL для миграций ниже.

4. Примени миграции к тестовой базе и запусти тесты.

   Bash (macOS/Linux):

   ```bash
   DATABASE_URL='postgresql://postgres:postgres@localhost:5432/fakegram_e2e' npx prisma migrate deploy
   npm run test:e2e
   ```

   PowerShell (Windows):

   ```powershell
   $previousDatabaseUrl = $env:DATABASE_URL
   try {
     $env:DATABASE_URL = 'postgresql://postgres:postgres@localhost:5432/fakegram_e2e'
     npx.cmd prisma migrate deploy
     if ($LASTEXITCODE -ne 0) { throw 'E2E database migration failed' }
   } finally {
     if ($null -eq $previousDatabaseUrl) {
       Remove-Item Env:DATABASE_URL -ErrorAction SilentlyContinue
     } else {
       $env:DATABASE_URL = $previousDatabaseUrl
     }
   }
   npm.cmd run test:e2e
   ```

   Prisma CLI читает `DATABASE_URL` из `prisma.config.ts`; `E2E_DATABASE_URL`
   из `.env.test.local` используется конфигурацией Vitest. Поэтому при
   миграциях URL задаётся отдельно. Bash ограничивает его одной командой,
   а блок PowerShell восстанавливает прежнее значение даже при ошибке.
   `.env` с базой разработки остаётся прежним.

Для последующих запусков достаточно поднятой БД с актуальными миграциями и
`npm run test:e2e`. После появления новых миграций повтори шаг 4.

По умолчанию конфигурация читает локальный `DATABASE_URL` из окружения или
`.env` и заменяет имя базы на `fakegram_e2e`. Обычный `.env` остаётся прежним.
Для другого подключения задай `E2E_DATABASE_URL` в окружении или в
игнорируемом файле `.env.test.local`. URL обязан указывать на `fakegram_e2e`;
другая база отклоняется до запуска тестов. Для удалённого сервера нужен явно
заданный `E2E_DATABASE_URL`.

Учётные данные в репозиторий добавлять не нужно. Остальные настройки запуска
тестовые: `NODE_ENV=test`, отдельный JWT-секрет, срок access-токена 15 минут,
refresh-токена 30 дней и `COOKIE_SECURE=false` для локального HTTP.

### Покрытие auth-флоу

В `test/auth.e2e-spec.ts` находятся 26 сценариев для задачи #56:

| Запрос                                 | Проверки                                                                                                 |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `POST /auth/register`                  | Успешная регистрация, занятые email и username, невалидное тело                                          |
| `POST /auth/login`                     | Успешный вход, неправильный пароль, неизвестный email                                                    |
| `POST /auth/refresh`                   | Ротация токена, отсутствующая и пустая cookie, неизвестный и просроченный токен, повторное использование |
| `GET /auth/me`                         | Публичный профиль, некорректный `sub`, удалённый пользователь                                            |
| Защищённые `/auth/me` и `/auth/logout` | Отсутствующий, некорректный и просроченный access-токен                                                  |
| `POST /auth/logout`                    | Пустой ответ `204`, очистка cookie, отзыв всех refresh-сессий пользователя                               |
| Полная цепочка                         | `register → login → refresh → me → logout` с автоматической передачей cookie                             |

Используется Vitest, как и в unit-тестах проекта. Отдельный Jest-конфиг,
упомянутый в исходном issue, не нужен: его роль выполняет
`vitest.e2e.config.mts`, а `npm run test:e2e` запускает именно его.

### Что проверяется внутри тестов

`POST /auth/register` должен вернуть `201`, публичного пользователя и
валидный access-токен. Refresh-токен передаётся через cookie с `HttpOnly`,
`SameSite=Strict` и `Path=/auth/refresh`, а в БД хранится его SHA-256.
Хеш пароля и refresh-токен отсутствуют в JSON-ответе.

Повторная регистрация с занятым email или username должна вернуть `409`
без новой cookie. Для каждой проверки второе уникальное поле отличается:
так тест не перепутает причины конфликта. После отказа данные пользователя
и его исходной refresh-сессии должны остаться прежними; второй пользователь
не создаётся.

Параметризованный тест `it.each` отдельно отправляет невалидный email, слабый
пароль и лишнее поле `role`. Каждый запрос должен получить `400` с сообщением
о соответствующей ошибке, без cookie и без создания пользователя или токенов.
Эти сценарии проверяют настоящую валидацию DTO и `forbidNonWhitelisted` в
общем `ValidationPipe`.

Успешный вход создаёт независимое семейство refresh-токенов. При обновлении
сессии старый токен становится использованным, новый сохраняет то же
семейство, а в cookie возвращается новое случайное значение. Повторное
использование старого токена отзывает всё это семейство, включая его новый
токен, но сохраняет независимую сессию входа.

Access-токен проверяется настоящим `JwtService`: подпись, срок действия и
поля `sub` и `username`. Тест не требует, чтобы две JWT-строки обязательно
различались: при одинаковых данных и выпуске в одну секунду JWT могут
совпасть. Refresh-токены при ротации обязаны отличаться.

Для проверки истечения refresh-токена тест устанавливает его `expiresAt`
в прошлое непосредственно в тестовой базе. Просроченный JWT подписывается
с `expiresIn: -1`. Ожидание по таймеру и подмена системных часов не нужны.

В полной цепочке используется `request.agent`: Supertest сохраняет cookie
из ответов и сам отправляет их с учётом пути. После logout cookie удаляется,
все refresh-сессии пользователя исчезают из БД, а следующий refresh получает
`401`. Выход не отзывает уже выданные access-токены: они действуют до своего
срока истечения.

Перед тестом создаётся уникальный набор данных регистрации. После теста
удаляются только его пользователи по уникальным email или username;
связанные refresh-токены удаляются каскадно. Перед HTTP-запросами
дополнительно проверяется имя подключённой базы.

Новое приложение создаётся перед каждым сценарием и закрывается после него.
Это также сбрасывает настоящее хранилище ограничителя запросов между тестами:
в обычном auth-флоу ограничения остаются включёнными, а независимые тесты
не расходуют лимиты друг друга.
